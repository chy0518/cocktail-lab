# 调酒实验室 设计方案

## 1. 项目概述

### 1.1 作品名称
《调酒实验室》

### 1.2 一句话定义
一款竖屏、纯离线、可直接体验的自由调酒互动作品。用户在同一张调酒台上逐步选择基酒、辅料、风味材料、调制方式和杯型，实时看到杯中状态变化，最终生成一杯可命名、可署名、可保存海报的专属鸡尾酒。

### 1.3 核心体验目标
本作品不强调任务、分数或挑战，而强调以下三点：

1. 调酒过程有持续反馈，用户能明显感到“我真的在做一杯酒”。
2. 最终成品稳定好看，适合保存或分享。
3. 流程简单直观，评委和普通用户点开即可玩懂。

### 1.4 MVP 定位
本项目采用“强视觉展示型”MVP：

1. 不做顾客需求、经营玩法、评分系统、闯关目标。
2. 不做复杂液体物理模拟。
3. 不做多模板海报编辑器。
4. 把开发重心放在单页工作台体验、实时视觉反馈和最终海报质感上。

---

## 2. 赛题约束与实现边界

### 2.1 交付形式
最终交付为可直接运行的前端离线项目：

1. 入口文件必须为 `index.html`。
2. 可采用单文件或多文件结构。
3. 若为多文件结构，`index.html` 仅可通过相对路径引用本地资源。

推荐结构：

```text
/
  index.html
  /css
    main.css
  /js
    main.js
    config.js
    state.js
    render.js
  /images
  /audio
```

### 2.2 必须满足的技术规则

1. 整个作品必须纯离线运行。
2. 禁止任何网络请求行为，包括但不限于 `fetch`、`XMLHttpRequest`、`axios`、`WebSocket`。
3. 禁止使用任何外部 CDN、在线字体、外部图片或脚本资源。
4. 禁止任何外部跳转，不使用外链 `<a>`、`window.location` 等方式跳出作品。
5. 打包为 zip 后总体积必须小于 `8MB`。
6. 页面需适配主流移动端竖屏，无横向滚动条。
7. 若使用本地存储，优先使用 `localStorage`。

### 2.3 错误处理要求
项目必须包含统一的错误捕获逻辑。页面初始化和关键交互更新需包裹在 `try-catch` 中；一旦出现异常，页面应显示统一友好提示：

`哎呀，出错了，请重启试试吧~`

## 3. 产品定位与设计原则

### 3.1 产品定位
《调酒实验室》不是模拟真实酒吧工作流，也不是专业调酒教学工具，而是一款偏作品感、偏视觉审美、偏分享表达的互动体验。

### 3.2 设计原则

1. 用户是在“调一杯酒”，不是“填写一个表单”。
2. 动画只做反馈，不做复杂表演。
3. 结果优先保证好看，而不是追求严格写实。
4. 所有规则都服务于“稳定产出一杯值得保存的酒”。
5. 视觉风格统一优先于功能堆叠。

---

## 4. 视觉方向

### 4.1 总体风格
作品采用：

`暖夜酒吧像素风`

风格关键词：

1. 像素化造型
2. 温暖、安静、克制
3. 深夜酒吧氛围
4. 轻高级感
5. 低饱和但不灰暗

### 4.2 视觉气质说明
本项目不是传统高饱和可爱像素游戏，也不是写实酒液模拟，而是“像素材质 + 高级配色 + 轻氛围光效”的方向。这样既适合程序绘制，也更容易统一杯子、桌面、装饰和海报。

### 4.3 色彩原则

1. 背景以深棕、深墨绿、暖黑、酒红褐为主。
2. 酒液颜色采用风格化预设色域，不做真实颜料混色。
3. 高光以奶油白、暖金、浅青绿等低面积亮色为主。
4. 动效颜色尽量从主色域衍生，不额外引入杂色。

---

## 5. 页面结构

### 5.1 整体结构
整个作品采用竖屏单页工作台结构，核心页面固定为同一张调酒台，不做多页频繁切换。

页面分为 4 个主要区域：

1. 顶部信息条
2. 中上主舞台
3. 中下操作面板
4. 底部控制区

### 5.2 顶部信息条
负责显示：

1. 作品标题 `调酒实验室`
2. 当前步骤名称
3. 当前进度信息

这一块高度应尽量克制，避免挤占主舞台空间。

### 5.3 中上主舞台
这是作品最核心的可视区域，始终固定显示调酒台场景，包括：

1. 桌面背景
2. 主杯子或雪克杯
3. 杯中酒液
4. 轻量粒子/波纹/高光层
5. 风味材料展示托盘

### 5.4 中下操作面板
根据当前步骤显示不同的操作内容：

1. 基酒卡片
2. 辅料卡片
3. 风味材料卡片
4. 调制方式按钮
5. 杯型选择卡片
6. 海报填写表单与主题切换

### 5.5 底部控制区
始终显示以下核心按钮：

1. `上一步`
2. `撤销上一份`
3. `下一步`

## 6. 流程设计

最终确认的步骤顺序如下：

1. 基酒
2. 辅料
3. 风味材料
4. 调制方式
5. 杯型
6. 海报

### 6.1 欢迎态
可选保留一个非常简短的开始界面，仅用于展示标题和进入按钮。该界面不应拖慢体验，建议一屏内完成。

### 6.2 Step 1：基酒

规则：

1. 只能选择 `1 种` 基酒。
2. 基酒份数为 `1-4 份`。
3. 点击当前基酒会增加 1 份。
4. 点击其他基酒会自动替换当前基酒，并重置为 1 份。
5. 必须选中基酒后才可进入下一步。

### 6.3 Step 2：辅料

规则：

1. 可选择 `0-2 种` 辅料。
2. 每种辅料可多次加入，以份数体现。
3. 若已选满 2 种辅料，再点第三种时仅提示上限，不自动替换。
4. 不强制必须选择辅料。

### 6.4 Step 3：风味材料

规则：

1. 可选择 `0-2 种` 风味材料。
2. 风味材料不进入制作中酒液主体。
3. 选中后显示在配料托盘中。
4. 再点同一项即取消选中。
5. 不强制必须选择风味材料。

### 6.5 Step 4：调制方式

单选项：

1. 摇和
2. 搅拌
3. 轻倒分层
4. 直接兑和

规则：

1. 必须选择一种调制方式才可继续。
2. 选择 `摇和` 时，优先尝试手机晃动交互。
3. 若设备不支持传感器或在桌面端，则回退为 `点击摇匀`。
4. 只有完成摇匀动作后，该步骤才算完成。
5. 其他调制方式选中后直接触发短动画并生效。

### 6.6 Step 5：杯型

单选项：

1. 长饮杯
2. 古典杯
3. 马天尼杯
4. 香槟杯
5. 高脚杯

规则：

1. 必须选择一种杯型。
2. 允许反复切换查看效果。

### 6.7 Step 6：海报

功能：

1. 输入酒名
2. 输入一句话介绍
3. 输入署名/心情
4. 切换背景主题
5. 预览最终海报
6. 保存海报

---

## 7. 交互规则

### 7.1 通用规则

1. `上一步` 只改变当前步骤，不清空已选内容。
2. 回到前面步骤后允许继续修改。
3. 每次有效操作都要即时刷新舞台。
4. `下一步` 仅在满足当前步骤最低条件时生效。

### 7.2 撤销上一份

`撤销上一份` 仅服务真正的加料动作。

它只记录并回退：

1. 加入基酒 1 份
2. 加入辅料 1 份

它不作用于：

1. 风味材料的勾选/取消
2. 调制方式切换
3. 杯型切换
4. 海报输入

### 7.3 风味材料的修改方式
风味材料通过“再次点击同一项取消”来完成修改，不进入撤销动作栈。

## 8. 实时反馈与动画原则

### 8.1 核心要求
制作过程中的酒液必须实时更新，而不是只在最终出品时出现。

实时更新分为两层：

1. 制作中实时变化
2. 最终成品升级展示

### 8.2 制作中实时变化
用户每次加入基酒或辅料后，杯中立即发生变化：

1. 液面上升
2. 主色域变化
3. 明暗和清透度变化
4. 气泡变化
5. 冰块变化
6. 顶部亮层或轻泡沫变化

### 8.3 风味材料反馈
风味材料不改变中途酒液主体，但会即时出现在托盘区域，形成“已备好风味装饰”的感觉。

### 8.4 调制方式反馈

1. 摇和：短晃动 + 混匀
2. 搅拌：轻旋转波纹
3. 轻倒分层：上下层次显现
4. 直接兑和：保留通透和气泡感

### 8.5 动画执行原则

1. 动画尽量简单，优先稳定和流畅。
2. 所有单次演出控制在 `1-2 秒内`。
3. 每次加料仅保留必要反馈，例如短倒入、液面变化、轻波纹。
4. 若某项效果不稳定或观感不佳，应优先删减而不是保留。
5. 所有效果以移动端性能优先。

---

## 9. 视觉计算规则

### 9.1 总体策略
采用“风格化规则”而非“真实混色”。

目标是保证：

1. 结果稳定好看
2. 参数好调
3. 像素风视觉统一
4. 不会因为多材料叠加出现脏色

### 9.2 预设色域
系统预设有限数量的主色域，材料只负责把结果推向某个色域，而不是直接做 RGB 平均混色。

建议色域：

1. `crystal`
2. `lime`
3. `amber`
4. `tea`
5. `berry`
6. `sunset`
7. `cola`
8. `ocean`

### 9.3 制作中计算逻辑
制作中只考虑：

1. 基酒
2. 辅料

通过这两类数据计算：

1. 液面高度
2. 主色域
3. 深浅档位
4. 清透度档位
5. 气泡档位
6. 冰块档位
7. 顶部亮层档位

### 9.4 最终成品修饰逻辑
最终出品时再叠加：

1. 风味材料
2. 调制方式
3. 杯型

风味材料只负责：

1. 点缀色
2. 装饰物
3. 海报中的视觉亮点

它们不应推翻制作阶段已经形成的主体色域。

### 9.5 档位制原则
为降低实现复杂度和提升调参稳定性，以下效果建议采用档位制：

1. 清透度：`1-5`
2. 深浅度：`1-5`
3. 气泡：`0-3`
4. 冰块：`0-3`
5. 顶部亮层：`0-3`

## 10. 材料配置表

### 10.1 基酒字段

```js
{
  id,
  name,
  paletteBias,
  strength,
  clarity,
  fillUnit
}
```

字段说明：

1. `paletteBias`：主色域倾向
2. `strength`：对主色域的影响强度
3. `clarity`：清透度基线
4. `fillUnit`：每一份增加的液面量

### 10.2 辅料字段

```js
{
  id,
  name,
  paletteBias,
  strength,
  clarityShift,
  fillUnit,
  bubbleLevel,
  iceLevel,
  foamLevel,
  layerWeight
}
```

字段说明：

1. `clarityShift`：清透度修正
2. `bubbleLevel`：气泡效果档位
3. `iceLevel`：冰块效果档位
4. `foamLevel`：顶部亮层或轻泡沫档位
5. `layerWeight`：分层表现时的轻重倾向

### 10.3 风味材料字段

```js
{
  id,
  name,
  accentPalette,
  accentStrength,
  garnish,
  trayIcon
}
```

字段说明：

1. `accentPalette`：最终点缀色域
2. `accentStrength`：点缀强度
3. `garnish`：装饰物类型
4. `trayIcon`：托盘显示图标类型

### 10.4 调制方式字段

```js
{
  id,
  name,
  mixMode,
  clarityShift,
  blendStrength,
  bubbleKeep,
  animationKey
}
```

### 10.5 杯型字段

```js
{
  id,
  name,
  shape,
  fillMask,
  garnishAnchor,
  scaleBias
}
```

### 10.6 色域字段

```js
{
  id,
  baseColor,
  lightColor,
  deepColor,
  foamColor,
  bubbleColor
}
```

## 11. 状态模型

### 11.1 流程状态

```js
{
  currentStep,
  methodReady
}
```

### 11.2 配方状态

```js
{
  baseSelection,
  mixerSelections,
  flavorSelections,
  methodSelection,
  glassSelection
}
```

示例：

```js
baseSelection = { id: "whiskey", pours: 2 }
mixerSelections = [
  { id: "cola", pours: 2 },
  { id: "ice", pours: 1 }
]
flavorSelections = ["lime"]
methodSelection = "built"
glassSelection = "highball"
```

### 11.3 动作历史

```js
[
  { type: "add-base", id: "whiskey" },
  { type: "add-mixer", id: "cola" },
  { type: "add-mixer", id: "cola" }
]
```

该历史仅用于支持 `撤销上一份`。

### 11.4 派生视觉状态
不建议将视觉值作为长期源状态存储，而应在每次渲染前根据当前配方重新计算。

制作中视觉结果建议统一组织为：

```js
{
  fillLevel,
  paletteKey,
  toneLevel,
  clarityLevel,
  bubbleLevel,
  iceLevel,
  foamLevel
}
```

最终成品视觉结果建议统一组织为：

```js
{
  paletteKey,
  accentKeys,
  garnishes,
  layerMode,
  glassShape,
  highlightStyle
}
```

### 11.5 海报状态

```js
{
  posterTheme,

  cocktailNote,
  signature
}
```

## 12. 视觉计算流水线

每次用户操作后，程序按以下顺序更新结果：

1. 记录有效动作
2. 汇总当前配方
3. 计算制作中酒液
4. 叠加调制方式修正
5. 叠加最终风味和杯型修饰
6. 输出海报可用结果

### 12.1 记录动作
只有基酒和辅料的加入动作进入动作历史。

### 12.2 汇总当前配方
根据已选内容整理当前有效配方。

### 12.3 计算制作中酒液
根据基酒和辅料得出：

1. 液面高度
2. 主色域
3. 深浅
4. 清透度
5. 气泡
6. 冰块
7. 顶部亮层

### 12.4 调制方式修正
根据选中的调制方式对制作中的结果进行修正。

### 12.5 最终成品修饰
叠加风味点缀、装饰物、杯型裁切和最终高光。

### 12.6 海报结果整理
将最终成品视觉结果和用户输入文本组合为海报预览数据。

## 13. 经典配方彩蛋

### 13.1 总原则
经典配方用于增加惊喜感，不用于判定作品成败。

### 13.2 匹配方式
采用轻量打分制，而非严格配方校验。

单个经典款可按下列维度打分：

1. 基酒命中
2. 辅料命中
3. 风味材料命中
4. 调制方式命中
5. 杯型命中

达到阈值即判定命中彩蛋。

### 13.3 建议经典款

1. 金汤力
2. 自由古巴
3. 威士忌酸
4. 龙舌兰日出
5. 蔓越莓伏特加
6. 若规则适配可再增加 1-2 个单基酒经典款

### 13.4 展示时机
经典彩蛋建议在海报页显示，而不是中途弹出打断流程。

展示形式建议为小徽章或小卡片，例如：

`经典款彩蛋：自由古巴`

## 14. 海报生成规则

### 14.1 总体原则

1. 只保留一个固定版式。
2. 允许切换背景主题。
3. 内容自动排版，不做复杂手动编辑。
4. 最终酒杯必须是海报视觉主角。

### 14.2 海报结构
从上到下分为 5 个区域：

1. 顶部标题区
2. 主视觉酒杯区
3. 酒名区
4. 信息区
5. 署名区

### 14.3 海报内容

固定包含：

1. 作品名 `调酒实验室`
2. 最终鸡尾酒大图
3. 酒名
4. 一句话介绍
5. 配方摘要
6. 署名/心情
7. 经典彩蛋提示（仅命中时显示）

### 14.4 配方摘要格式
配方摘要保持精简，例如：

`威士忌 / 可乐 / 青柠 / 直接兑和`

### 14.5 背景主题
建议保留 3 套主题：

1. 暖夜黑金
2. 日落橙粉
3. 海洋蓝绿

这些主题只修改：

1. 背景渐变
2. 粒子颜色
3. 边缘高光
4. 局部强调色

不改变整体版式。

### 14.6 文本长度限制

1. 酒名：最多 `12` 个中文字符
2. 一句话介绍：最多 `36` 个中文字符
3. 署名/心情：最多 `12` 个中文字符

前端应主动限制输入长度，避免海报排版溢出。

### 14.7 保存方式
海报区域最终需支持导出或保存为图片。

离线条件下建议做法：

1. 使用前端 `canvas` 将海报区域绘制为 PNG
2. 桌面端触发下载
3. 移动端提供长按保存提示或保存按钮

## 15. 组件划分建议

建议组件/模块拆分如下：

1. `AppShell`：整体结构
2. `StepHeader`：顶部步骤信息
3. `MixStage`：主舞台容器
4. `BarTable`：桌面和背景氛围
5. `CocktailVessel`：杯型和酒液绘制核心
6. `PourEffectLayer`：短时加料动画
7. `FlavorTray`：风味托盘
8. `OptionPanel`：当前步骤操作区
9. `IngredientCard`：材料卡片
10. `MethodPanel`：调制方式选择
11. `GlassPanel`：杯型选择
12. `BottomControls`：底部按钮
13. `PosterPreview`：海报预览与导出

若最终采用原生 HTML/CSS/JS 实现，这些组件可以是模块化函数或渲染单元，不要求必须使用框架。

## 16. 技术实现建议

### 16.1 技术栈
建议采用最稳妥的纯前端方案：

1. `HTML`
2. `CSS`
3. `原生 JavaScript`

理由：

1. 更容易控制离线交付。
2. 不依赖构建工具也可直接运行。
3. 便于最终打包为可提交作品。

### 16.2 文件形式建议
优先推荐多文件结构，而不是所有逻辑塞进单个 `index.html`。原因是：

1. 便于拆分配置表
2. 便于维护绘制逻辑
3. 便于后续快速调整视觉参数

推荐结构：

```text
/
  index.html
  /css
    main.css
  /js
    config.js
    state.js
    logic.js
    render.js
    poster.js
    main.js
```

### 16.3 渲染建议

1. 杯子和酒液可优先使用 `HTML + CSS + SVG` 或 `Canvas` 之一实现。
2. 若更强调像素风裁切和导出一致性，可优先考虑 `Canvas`。
3. 若更强调布局和快速开发，可用 `HTML/CSS` 实现舞台、再用 `Canvas` 生成海报。

### 16.4 传感器交互建议
`摇和` 步骤可尝试使用 `DeviceMotionEvent`：

1. 若可用，允许摇动手机完成交互。
2. 若不可用，必须回退为点击按钮。
3. 不应把传感器能力作为强依赖。

### 16.5 性能建议

1. 避免重粒子系统。
2. 避免大面积模糊和复杂滤镜。
3. 复用渲染结果，尽量按需重绘。
4. 动画只针对局部元素更新。
5. 控制资源尺寸，避免项目体积逼近 8MB。

### 16.6 错误恢复建议

1. 初始化失败时显示统一报错文案。
2. 核心状态更新函数用 `try-catch` 包裹。
3. 若海报导出失败，应给出本地友好提示，而不是页面崩溃。

## 18. 验收标准

若第一版完成，至少应满足以下标准：

1. 手机竖屏下完整显示，无横向滚动。
2. 用户能在同一张工作台上完成全部调酒流程。
3. 基酒和辅料加入后，酒液有明显实时变化。
4. 风味材料能显示在托盘并影响最终装饰。
5. 四种调制方式均有可感知的轻量反馈。
6. 杯型切换后成品形态明显不同。
7. 海报页能输入文本、切换背景并生成预览。
8. 命中经典款时能显示彩蛋信息。
9. 项目纯离线可运行，无外部资源依赖。
10. 页面异常时能显示统一友好报错文案。

## 20. 结论

《调酒实验室》的第一版最重要的不是“像真实调酒一样复杂”，而是：

1. 过程始终有反馈
2. 结果始终稳定好看
3. 用户能自然地产生“这是我亲手调出来的作品”的感觉

只要单页工作台、实时视觉变化、轻量调制反馈和海报预览这四件事做稳，这个作品就已经具备很强的黑客松展示力和评审友好度。
